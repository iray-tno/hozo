Hozo does not treat a dynamic `className` as a single thing to give up on.
There are three tiers, and only the last one costs anything at runtime.

**Static — compiled away.**

```tsx
<View className="p-4 bg-blue-500" />
```

Becomes a scoped class in a real stylesheet. Nothing is left at runtime.

**Structurally dynamic — compiled into a conditional.**

```tsx
import { cx, View } from '@hozo/core'

<View className={cx('p-4', active && 'bg-blue-500', size === 'lg' && 'text-xl')} />
```

The compiler does not need to know what `active` is. It keeps the shape of
the expression and compiles each branch, so all three classes are real CSS
and the choice between them is a boolean at runtime.

Here is a filter chip in that shape, rendered by this site's build. Open the
outputs: each `cx` becomes a conditional over class names that already exist
in the stylesheet, on the Web, and over `StyleSheet` entries on React Native.

  <div style={{ display: 'flex', gap: '8px', padding: '24px' }}>
    <Filter label="All" active />
    <Filter label="Open" active={false} />
    <Filter label="Closed" active={false} />
  </div>
</CompiledExample>

The shapes it reads are a string, `&&`, a ternary, a template literal, and a
call to `cx` from `@hozo/core`, or to a function imported from `clsx` or
`classnames`. Inside them, a part it cannot read, such as
a caller's `className`, falls back alone and the rest still compiles.

A project's own helper is not one of them, even when it only wraps those
libraries, as a `cn` in `@/lib/utils` often does. The compiler reads one
file at a time, so it cannot see what `cn` does, and the whole call takes the
runtime fallback below.

So Hozo follows the import to the helper's file and reads it. A
function that only hands its arguments to `clsx`, `classnames`, `cx`,
or `twMerge` is then read argument by argument (#964, #1676). Direct `twJoin`
calls compile when all class tokens are known and supported. Its opaque
arguments and wrappers stay at runtime to preserve array flattening;
`twJoin` does not share `clsx`'s object-dictionary semantics.

When the call uses `twMerge` — or a helper such as shadcn/ui's `cn` that
hands its result to `twMerge` — Hozo applies `tailwind-merge`'s conflict
resolution at compile time. Static conflicts (`twMerge('p-4', 'px-2')`) and
conditional overrides (`cn('px-3', active && 'px-2')`) are resolved into the
compiled rules and guards. This requires every possible class token to be
known and supported by the compiler. If any argument contains an opaque
caller class list (`cn('px-3 py-1 hover:bg-blue-500', className)`) or an
unsupported token, the whole merge stays at runtime. Custom classes and
ambiguous arbitrary values cannot be classified by prefix alone, and a
token removed by a later token must not suppress an earlier class.
On Native, a `Pressable` can apply runtime `hover:` and `active:` candidates
from the project map using its own interaction state. Runtime variant support
depends on what the candidate map can represent and what state the component
supplies. Custom mergers built with `extendTailwindMerge` or
`createTailwindMerge` also stay at runtime so their configured conflict groups
remain authoritative.

Anything else can be declared, and a declaration wins over what was found:

```ts
hozo({ classHelpers: [{ module: '@/lib/utils', name: 'cn' }] })
```

`module` is the specifier as callers write it, and `recognize: false` undoes
a function found automatically. The same option works for `withHozo` on
Metro. Vite resolves the import as the build does and re-reads the helper
when it changes. Metro reads helpers once when it starts, resolving relative
imports and tsconfig `paths`, so a helper edited while it runs needs a
restart, and one behind any other alias needs declaring. Or use `cx` from
`@hozo/core`, which needs neither.

**Truly dynamic — a runtime fallback.**

```tsx
<View className={classNameFromProps} />
```

Here the compiler genuinely cannot tell. Every class *any* source file in
the project mentions is scanned and emitted into one project-wide
stylesheet, so whatever the expression produces is already defined. The
scan is cached and incremental.

The theme behind all of this is read from the project's own Tailwind
entry stylesheet by running Tailwind's resolver, rather than by parsing a
config file — the same discipline the conformance suite uses when it asks
Tailwind for its own class list instead of keeping a copy. See the
[Tailwind CSS guide](../tailwind/) for how `@theme` tokens, variants and
React Native layout helpers work, or the [StyleX guide](../stylex/) for
combining static StyleX sheets with Tailwind in the same compiler pass.

To see it compiled, the [Tailwind page](../../../tailwind/) puts one component
beside the CSS and the `StyleSheet` the build makes from it, and the
[Conformance Matrix](../../../conformance/) shows class by class how close the
output is to Tailwind's own.
