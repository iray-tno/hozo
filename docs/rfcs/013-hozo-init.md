# RFC 013: `hozo init` — Hozo added to an existing project

- **Status**: Draft (§7: steps 1–4 implemented)
- **Authors**: iray-tno
- **Tracking issue**: Not assigned
- **Target packages**: `@hozo/cli`; `@hozo/compiler` (one analysis pass)
- **Baseline**: main `b3ea23ff` (2026-11-17)

## 1. Summary

RFC 011 reserved `hozo init`: add Hozo to a project that already builds,
detecting the framework and package manager, installing `@hozo/*` at one
version, making the edits each getting-started guide describes, and finishing
with `square`. It was deferred because editing six frameworks' configs safely
is larger than everything else in RFC 011.

This RFC specifies what `init` edits in each framework, how it edits a config
without rewriting it, what it does with a config it does not recognise, and
how it is kept equal to the guides.

The guides are not replaced. `init` makes the edits they describe, and CI
holds the two to one result (§7).

## 2. What the starters actually contain

The guides say "start from the framework's starter". Measured on the
starters' current releases (2026-11-17), the starters differ from the guides
in ways a newcomer would not see:

| Stack | Starter (version) | Config | Stylesheet | What `init` has to know |
| --- | --- | --- | --- | --- |
| Vite | `create-vite` 9.3.4, `react-ts` | `export default defineConfig({ plugins: [react()] })` | `src/index.css`, plain CSS | `src/index.css` is on Hozo's default stylesheet list, so a starter with no `css` option compiles against a stylesheet with no `@import "tailwindcss"` (`square`: `css-no-tailwind`) |
| Next.js | `create-next-app` 16.4.6 | `const nextConfig = {…}; export default nextConfig` | `app/globals.css`, with Tailwind (`app-tw`) or without | Without Tailwind, `app/globals.css` is Vite's case again: on the default list, no `@import "tailwindcss"`. With Tailwind, `@tailwindcss/postcss` already emits preflight; Hozo's would be a second copy |
| Metro, React Native CLI | `@react-native-community/template` 0.88.1 | `module.exports = mergeConfig(getDefaultConfig(__dirname), config)` | none | — |
| Metro, Expo | `expo-template-default` 58.0.34 | **none**: Expo uses its default Metro config until a project writes one | none | `init` creates `metro.config.js` from `expo/metro-config` |
| Astro | `withastro/astro` `examples/minimal` | `export default defineConfig({})` | none | No React integration: Astro needs `@astrojs/react` and the tsconfig `jsx` setting before any `.tsx` builds |
| TanStack Start | `TanStack/router` `examples/react/start-basic` | `defineConfig({ …, plugins: [tailwindcss(), tanstackStart(…), viteReact(), nitro()] })` | `src/styles/app.css`, `@import 'tailwindcss' source('../')`, through `@tailwindcss/vite` | `hozo()` goes first, before `tailwindcss()`, with `preflight: false` |

Storybook's `main.ts` is generated by `storybook init` rather than copied
from a template; its shape is `const config = { stories, addons, framework }`
followed by `export default config`.

Three of the six need something no guide says today (Vite's stylesheet,
Tailwind already present, Expo's missing config). Those are fixed in the
guides by step 1 (§7), whether or not `init` ships.

## 3. Command

```
hozo init                      # dry run: what it would install, create and edit
hozo init --write
hozo init --ui --write         # @hozo/ui and its theme as well
hozo init --css <file>         # the stylesheet to use or create
hozo init --no-install         # edit only; print the install command
```

1. **Detect.** The stack is read from the config files `square` already
   knows (`vite.config.*`, `astro.config.*`, `next.config.*`,
   `metro.config.*`, `.storybook/main.*`) and from `package.json`: `expo`
   with no `metro.config.*` is Metro. A project with two (Next.js and
   Storybook, say) gets both edited, except Storybook beside a Vite config,
   which builds with that config (§7.4). None found exits `2` with the list of
   stacks `init` knows; a workspace root with no bundler config of its own is
   told to run `init` in the package that builds.
2. **Install.** The adapter (`@hozo/vite`, `@hozo/next`, `@hozo/metro` or
   `@hozo/storybook`) and `@hozo/compiler` as dev dependencies, `@hozo/core`
   as a dependency, `@hozo/ui` with `--ui`. Every `@hozo/*` package is
   released at one version (`.changeset/config.json`: `fixed`), so `init`
   installs the version of the `@hozo/cli` running it, with the project's
   package manager (the detection `add` already has). A project that already
   has an `@hozo/*` package at another version is not upgraded: `init` exits
   `2` and names `square`'s `version-mismatch` finding. The dry run and
   `--no-install` print the command instead of running it.
3. **Stylesheet** (§5).
4. **Config** (§4).
5. **`square --setup`** runs in-process and its findings print under `init`'s
   own. With `--write`, a setup error after the edits exits `1`: `init` did
   what it said and the project still does not build with Hozo, which is
   what `1` means.

It follows RFC 011's conventions: the write contract (§3.4), `--format json`,
exit codes `0`/`1`/`2`, and every prompt a flag (there are none).

## 4. Editing a config without rewriting it

A config is the one file in a project most likely to have been written by
hand, and the one that breaks the build when it is wrong. So:

- **Spans, not printing.** `init` never prints a config from a syntax tree.
  A new pass in `@hozo/compiler` parses the config with the compiler's own
  parser and returns insertions at offsets (`{ start, end, replacement }`),
  as `dry-fit --fix` already does with `reactNativeImportFix` (#1053).
  Everything `init` does not insert stays byte for byte, comments and
  formatting included.
- **Known shapes, or nothing.** The pass recognises each shape in the table
  below and nothing else. A config it does not recognise (a computed export,
  a `plugins` array built elsewhere, a config that is a function of `env`)
  is not edited: `init` prints the lines to add, the guide's link, and exits
  `2`. A wrong edit to a config is worse than no edit, because it fails at
  build time in a file the project did not ask `init` to understand.

| Stack | Recognised | Inserted |
| --- | --- | --- |
| Vite, TanStack Start | `export default defineConfig({ … plugins: [ … ] … })`; the object directly exported | `import { hozo } from '@hozo/vite'`, and `hozo(…)` as the array's first element |
| Astro | `export default defineConfig({ … })` | `vite: { plugins: [hozo(…)] }`, or `hozo(…)` first in an existing `vite.plugins` |
| Next.js | `export default <identifier>` or `export default { … }`; `module.exports =` the same | `withHozo(<expression>, { … })` around the exported expression |
| Metro | `module.exports = <expression>` | `withHozo(<expression>, { … })`; with Expo and no config, a new `metro.config.js` |
| Storybook | an `addons: [ … ]` array in the exported object, with a Vite framework | `{ name: '@hozo/storybook', options: { css } }` as its last element |

The import goes after the file's last import, in the file's own quote style
and semicolon use, which the pass reads from the file's existing imports.
A config that already imports the adapter and calls it is left alone, and a
second run reports nothing to do.

**Tailwind already present** (`@tailwindcss/vite`, `@tailwindcss/postcss`,
or a stylesheet that imports `tailwindcss` and is already in the build):
`init` passes `preflight: false` and, on Vite, puts `hozo()` before
`tailwindcss()`. This is the Astro guide's rule, applied wherever it holds.

**Astro without React** is not completed by `init`. Adding an integration is
`astro add react`'s job, which edits the same config and the tsconfig;
`init` exits `2` and says to run it first. Running another tool's
configurator from inside `init` would put two writers on one file in one
command.

## 5. The stylesheet

`init` always passes `css` explicitly, so the project never depends on the
default list (§2: Vite's starter is the case where the list picks the wrong
file).

1. `--css <file>` is used as given; if it does not exist it is created.
2. Otherwise, a stylesheet the build already uses that imports `tailwindcss`
   (Next.js `app-tw`'s `app/globals.css`, TanStack's `src/styles/app.css`) is
   used, and nothing is added to it except `@hozo/ui`'s theme with `--ui`.
3. Otherwise `src/theme.css` (`theme.css` at the root without `src/`) is
   created, as the guides have it:

   ```css
   @import "tailwindcss";

   @theme {
   }
   ```

   Hozo reads this file; it does not have to be imported anywhere, and
   `init` does not import it. A project that wants it on the page imports it
   like any other stylesheet.

With `--ui`, `@import "@hozo/ui/theme.css";` goes after `@import
"tailwindcss"`, which is the line `square`'s `css-no-ui-theme` finding asks
for.

## 6. What `init` does not do

- **Rewrite components.** Moving a React Native project's imports is
  `dry-fit`'s; `init` ends by naming it when `react-native` is a dependency.
- **Native project files.** The React Native 0.87 `androidx.collection` pin
  is printed, not written; `android/app/build.gradle` is the platform's.
- **Create a project.** `npm create hozo` (RFC 011 §7) runs a framework's
  own creator and then `init`; it is a later RFC that depends on this one.

### 7.1 Step 1

The Vite, Next.js, Metro and TanStack Start guides say what §2 found. The
starters' files are in `scripts/fixtures/starters/`, one directory per
starter (Next.js twice: with and without Tailwind), with where each came
from in `sources.json`; Biome skips the directory so their own quotes and
semicolons stay. TanStack's `@import 'tailwindcss' source('../')` was loaded
through `@hozo/tailwind`'s `loadTheme`, static and not: both read the
stylesheet's `@theme`, so `init` can point `css` at it unchanged.

### 7.2 Step 2

`configShape` in `@hozo/compiler/analysis` (`crates/hozo_parser/src/config_shape.rs`)
reports a config's imports and requires, its `export default` or
`module.exports`, top-level bindings, and the objects, arrays, calls and
strings under them to six levels, each with UTF-16 offsets and, inside an
object, where the whole property starts. It looks through parentheses, `as`,
`satisfies` and `!`, and recognises nothing: `packages/cli/src/init-config.mjs`
decides which shapes are known.

`hozo init` edits Vite, TanStack Start and Astro. On the starters:

| Starter | Stylesheet | Config edit |
| --- | --- | --- |
| Vite | `src/theme.css` created (not `src/index.css`) | import after the last import; `hozo({ css: 'src/theme.css' })` first in `plugins`, inline as the array is |
| TanStack Start | `src/styles/app.css`, unchanged | `hozo({ css: 'src/styles/app.css', preflight: false })` on its own line before `tailwindcss()` |
| Astro (with `@astrojs/react`) | `src/theme.css` created | `vite: { plugins: [hozo(…)] }` into `defineConfig({})`, with the file's semicolons |

A second run on each reports nothing to install or edit. A config exporting
`defineConfig(({ mode }) => …)` exits `2` with the call to add and leaves
the file and `package.json` as they were; so do an uncommitted config, an
`@hozo/*` package at another version, Astro without React, and Next.js or
Expo (steps 3 and 4).

On the Vite starter with `@hozo/core`, `@hozo/vite` and `@hozo/compiler`
linked from this checkout, `hozo init --write` followed by the real
`square --setup` passed `versions`, `peers`, `adapter` and `css`. With
`--no-install` and packages still to install, `square` is not run: it
would only say the project has no `@hozo/*` dependency.

### 7.3 Step 3

Next.js and Metro configs are edited by wrapping the exported expression,
`export default` or `module.exports`, in `withHozo(…, { css })`, with the
import or `require` added after the file's last one in its own style. The
expression itself is not touched, so React Native's
`mergeConfig(getDefaultConfig(__dirname), config)` and Next's `nextConfig`
binding stay as written. Expo with no `metro.config.*` gets one from
`expo/metro-config`, as the Metro guide now shows. Metro is never passed
`preflight`: it is a Web reset.

| Starter | Stylesheet | Config edit |
| --- | --- | --- |
| Next.js | `theme.css` created (not `app/globals.css`, which has no Tailwind) | `export default withHozo(nextConfig, { css: "theme.css" });` |
| Next.js with Tailwind | `app/globals.css`, unchanged | `withHozo(nextConfig, { css: "app/globals.css", preflight: false })` |
| React Native | `theme.css` created | `withHozo(mergeConfig(getDefaultConfig(__dirname), config), { css: 'theme.css' })` |
| Expo | `src/theme.css` created | `metro.config.js` created |

A config exporting a function (`export default (phase) => ({ … })`) exits
`2` with the `withHozo` call to write. With `@hozo/core`, the adapter and
`@hozo/compiler` linked from this checkout, `init --write` and the real
`square --setup` passed `versions`, `peers`, `adapter` and `css` on both
the Next.js and the React Native starter.

Diffs now print a changed line's removal before its addition, as `diff -u`
does; the longest-common-subsequence tie went the other way before.

### 7.4 Step 4

Storybook's `main.*` gets `{ name: '@hozo/storybook', options: { css } }`
last in `addons`, after a trailing comma when the array has one, or a new
`addons` array when it has none. Storybook merges an addon's `options` into
the options its presets are called with (`combinedOptions` in Storybook
10.6.3), so `css` reaches `viteFinal`. A framework that does not build with
Vite (`@storybook/nextjs`) is refused with `storybook-not-vite`: the addon is
a `viteFinal` hook and would not run.

**Storybook beside a Vite config is not edited.** Storybook's Vite builder
loads the project's `vite.config.*` (`loadConfigFromFile` in
`@storybook/builder-vite`, unless `viteConfigPath` says otherwise), so a
config with `hozo()` already gives Storybook Hozo. Adding the addon as well
runs Hozo twice, and that is not harmless: `examples/login-demo` built with
`plugins: [hozo(), hozo(), react()]` emitted 6,140 bytes of CSS against
6,765 with one `hozo()`, missing ten rules (the `hozo-scroll-view` base
rules, the five `data-hozo-pointer-events` rules, and one component rule).
`init` skips the Storybook config there, installs no `@hozo/storybook`, and
says why. A project that followed both guides today has that duplication; it
is a bug of its own, outside `init`.

`--ui` was implemented in step 2.

## 8. Resolved questions

- **Install, or print the command?** Install with `--write`, print in a dry
  run and with `--no-install`. `add` installs nothing because a missing
  package there is the exception; for `init` installing is the point, and
  the version has one right answer (§3, step 2).
- **How to edit configs?** The compiler's parser through a narrow pass that
  returns span insertions (§4). Text matching would edit a commented-out
  `plugins:` line; a general config-editing library would be a second
  parser in the CLI, and one that reprints what it parses.
- **A config `init` cannot edit?** Not edited; the lines to add are printed
  and `init` exits `2` (RFC 011 §3.4). `init` never asks, so it runs the
  same in CI and in a terminal.
