# @hozo/cli

## 0.5.0

### Minor Changes

- [#1919](https://github.com/iray-tno/hozo/pull/1919) [`277361c`](https://github.com/iray-tno/hozo/commit/277361c7206e9d9080322e8a8d590b1a390df2f7) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo dry-fit --file-signal <name>=<regex>` counts the authored files whose source matches the pattern and reports the count as `corpusSignals.<name>`. It is the command-line form of the `fileSignals` option, so a corpus runner can use the same command as a user. The option can be repeated. A malformed name or pattern exits `2` with `[invalid-file-signal]`.

- [#1932](https://github.com/iray-tno/hozo/pull/1932) [`ddefc28`](https://github.com/iray-tno/hozo/commit/ddefc28020ed6d25723a811660c663e54081c02e) Thanks [@iray-tno](https://github.com/iray-tno)! - `@hozo/compiler/format-jsx` exports `formatJsx`, which lays out compiled JSX one element per line for a person to read. The compiler's own output stays on one line, so source positions hold. `hozo show` now prints its JSX through it, laid out the same way as the REPL's panes.

- [#1906](https://github.com/iray-tno/hozo/pull/1906) [`5f09276`](https://github.com/iray-tno/hozo/commit/5f09276ca888a122d38469a930d0f1f60ab759ae) Thanks [@iray-tno](https://github.com/iray-tno)! - Add `@hozo/cli`, the `hozo` command. `hozo dry-fit` (alias `migration-audit`) runs the migration audit with the same options and the same stdout and JSON. `hozo-migration-audit` keeps working for one minor release and prints a deprecation line on stderr.
  
  Exit codes are now `0` passed, `1` findings at or above `--fail-on`, `2` the command could not run. An input error (an unknown option, a missing checkout, an unreadable baseline) used to exit `1`, the same as a finding; it now exits `2` and ends its stderr line with a string code such as `[unknown-option]`.

- [#1919](https://github.com/iray-tno/hozo/pull/1919) [`9d20975`](https://github.com/iray-tno/hozo/commit/9d20975684383ed659085fc48dad34f70294505e) Thanks [@iray-tno](https://github.com/iray-tno)! - Add `hozo manifest` and `hozo links` to `@hozo/cli`. They run the same commands as `hozo-manifest` and `hozo-links`. Both old binaries keep working for one minor release and print a deprecation line on stderr.
  
  Both now use the `hozo` exit codes: `1` for a stale file under `--check`, and `2` for a command that could not run. A `2` ends its stderr line with a string code such as `[config-not-found]`. `hozo-links` used to exit `1` for configuration errors. `hozo-manifest` used to ignore unknown options and crash on a package it could not read.
  
  `hozo-links` now also runs when npm links it into `node_modules/.bin` as a symlink. Before, the linked binary did nothing and exited `0`.
  
  `@hozo/navigation` is an optional peer of `@hozo/cli`. Without it, `hozo links` exits `2` with `[missing-package]`.

- [#1927](https://github.com/iray-tno/hozo/pull/1927) [`9dff278`](https://github.com/iray-tno/hozo/commit/9dff278a4cf197716791f7c2530ae188789866f9) Thanks [@iray-tno](https://github.com/iray-tno)! - Add `hozo explain [CODE]`. It shows what a diagnostic means, a source that raises it, and the compiler's message for that source. Without a code, it lists every code. It accepts `aria-name-prohibited` as well as `ARIA_NAME_PROHIBITED`, and suggests close matches for an unknown code. `--format json` prints the entry.
  
  `@hozo/compiler` now ships `diagnostics.json`, the catalog `explain` reads. The catalog is generated from the compiler's own documentation of each code and from the conformance cases. `explain` reads only this file, so it compiles nothing and loads no native addon.

- [#1939](https://github.com/iray-tno/hozo/pull/1939) [`8947a3a`](https://github.com/iray-tno/hozo/commit/8947a3ab05048e54374a9394f88c7d42ca0b6d0d) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo show` now reports each class list in the file. For each list it gives the route: compiled, compiled under a condition, or resolved at runtime because the compiler cannot read it. For each class it says what became of it on the Web and on Native:
  
  - **compiled**;
  - **not-generated**: the theme has no Tailwind rule for it, so the class compiles to nothing;
  - **refused** or **not-wired** on Native: the compiler's reason is given;
  - **passed-through**: not a Tailwind class. The Web keeps it for the project's own CSS.
  
  The text report lists only the classes that did not compile everywhere. The JSON has every class under `classLists`.

- [#1932](https://github.com/iray-tno/hozo/pull/1932) [`7d3408b`](https://github.com/iray-tno/hozo/commit/7d3408b30957b65ee2d438d8d50aa253a8504713) Thanks [@iray-tno](https://github.com/iray-tno)! - Add `hozo show <file>`: it prints what one file compiles to, the way the REPL does, but with the project's theme.
  
  - The output: the Web JSX and CSS, the React Native JSX and StyleSheet, and each diagnostic with its line, column and the backends that raised it.
  - The theme comes from the stylesheet the project's bundler config names, else the usual names. `--css` names one directly.
  - `--web` or `--native` shows one platform. `--format json` and `--fail-on none|warning|error` are as on the other commands.

- [#1930](https://github.com/iray-tno/hozo/pull/1930) [`48d8ce9`](https://github.com/iray-tno/hozo/commit/48d8ce9a13e24acf6f790a282d437d9d2eae5814) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo square` now checks the code as well as the setup. After the setup checks, it runs the audit `hozo dry-fit` runs, against the stylesheet the css check found, and reports each error and warning where it is. The JSON report embeds the audit's report whole as `code.report`.
  
  - `--compare <report>` compares the code with a previous `hozo square --format json` or `hozo dry-fit` JSON report.
  - `--fail-on new-errors` fails only on code errors the baseline did not have. Setup errors still fail it.
  - A fatal setup finding, such as a bundler config without its Hozo adapter, skips the code half and says which check stopped it.
  - When the compiler cannot load, the setup report still prints, and the command exits 2.
  
  `@hozo/migration-audit` now exports `validateBaseline`.

- [#1927](https://github.com/iray-tno/hozo/pull/1927) [`ea85587`](https://github.com/iray-tno/hozo/commit/ea85587813aa3c7a59c5f37327b6c5ecaad969ee) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo square` now checks how the project wires Hozo in, as well as its packages:
  
  - **adapter**: each bundler config (Vite, Astro, Next.js, Metro, Storybook) uses its Hozo adapter, and that adapter is installed. On Vite, `hozo()` comes before React's plugin.
  - **css**: the stylesheet Hozo reads exists and imports Tailwind. When `@hozo/ui` is installed, it also imports `@hozo/ui/theme.css`. With no stylesheet at all, a warning says the classes compile against Tailwind's default theme.
  - **metro**: when `metro.config` changed after Metro last saved its state, a warning says to restart Metro with its cache cleared.
  - **scan**: every file that imports a runtime `@hozo/*` package was read by the last candidate scan. A file the scan missed gets no CSS on the Web.
  
  Config files are read as text, not run. A check that cannot see what it needs, such as a scan that has not run yet, says why and is skipped.

- [#1927](https://github.com/iray-tno/hozo/pull/1927) [`20c4543`](https://github.com/iray-tno/hozo/commit/20c4543916333ff1aec2ad2d87f23005e6b70585) Thanks [@iray-tno](https://github.com/iray-tno)! - Add `hozo square` (alias `doctor`), the check a project runs once it uses Hozo. It checks that every installed `@hozo/*` package is at one version, including a copy another package brought in at an older version, and that each package's peers, such as `react-native`, `react` and Expo's modules, are installed within the range the package declares. The ranges are read from the installed packages, so the check stays in step with them. `square` reads `package.json` files only and loads no compiler, so a broken install still gets a report. It exits `1` on a finding at or above `--fail-on` (default `error`) and `2` on a project with no `@hozo/*` dependency, which it points to `hozo dry-fit`.

- [#1946](https://github.com/iray-tno/hozo/pull/1946) [`225688d`](https://github.com/iray-tno/hozo/commit/225688dada614b75f9527f48e02c3d014681c586) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo show` now gives two more routes a class list can take:
  
  - **owner-callback**: on Native, the list is compiled into a callback that its pattern owner, such as a Chip or a Menu's items, applies with its own state.
  - **component**: the list is handed to a component the compiler does not lower, such as `@hozo/ui`'s `Button`, which resolves it. Before, such a list was not reported at all.
  
  Both come from new compiler evidence:
  
  - On Native, `tailwindPlan` now includes `ownerCallbacks` when there are any.
  - A compiler gains `componentClassLists(source)`, read from the same parse `compileNative` lowers.

- [#1943](https://github.com/iray-tno/hozo/pull/1943) [`b0f1e8c`](https://github.com/iray-tno/hozo/commit/b0f1e8c301478afdac7d0d3eed3cde911b22a72d) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo square` now says when the compiler that measured the code is not the one the project builds with. The code half compiles with the compiler the CLI brings, which `npx` may fetch at a newer version than the project's. It then reports a warning, `compiler-version-mismatch`, naming both versions and the `npx @hozo/cli@<version> square` that matches. The JSON gains `code.compiler` (`measuredWith`, `project`) and `code.findings`.
