# @hozo/migration-audit

## 0.5.0

### Minor Changes

- [#1919](https://github.com/iray-tno/hozo/pull/1919) [`277361c`](https://github.com/iray-tno/hozo/commit/277361c7206e9d9080322e8a8d590b1a390df2f7) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo dry-fit --file-signal <name>=<regex>` counts the authored files whose source matches the pattern and reports the count as `corpusSignals.<name>`. It is the command-line form of the `fileSignals` option, so a corpus runner can use the same command as a user. The option can be repeated. A malformed name or pattern exits `2` with `[invalid-file-signal]`.

- [#1906](https://github.com/iray-tno/hozo/pull/1906) [`5f09276`](https://github.com/iray-tno/hozo/commit/5f09276ca888a122d38469a930d0f1f60ab759ae) Thanks [@iray-tno](https://github.com/iray-tno)! - Add `@hozo/cli`, the `hozo` command. `hozo dry-fit` (alias `migration-audit`) runs the migration audit with the same options and the same stdout and JSON. `hozo-migration-audit` keeps working for one minor release and prints a deprecation line on stderr.
  
  Exit codes are now `0` passed, `1` findings at or above `--fail-on`, `2` the command could not run. An input error (an unknown option, a missing checkout, an unreadable baseline) used to exit `1`, the same as a finding; it now exits `2` and ends its stderr line with a string code such as `[unknown-option]`.

- [#1930](https://github.com/iray-tno/hozo/pull/1930) [`48d8ce9`](https://github.com/iray-tno/hozo/commit/48d8ce9a13e24acf6f790a282d437d9d2eae5814) Thanks [@iray-tno](https://github.com/iray-tno)! - `hozo square` now checks the code as well as the setup. After the setup checks, it runs the audit `hozo dry-fit` runs, against the stylesheet the css check found, and reports each error and warning where it is. The JSON report embeds the audit's report whole as `code.report`.
  
  - `--compare <report>` compares the code with a previous `hozo square --format json` or `hozo dry-fit` JSON report.
  - `--fail-on new-errors` fails only on code errors the baseline did not have. Setup errors still fail it.
  - A fatal setup finding, such as a bundler config without its Hozo adapter, skips the code half and says which check stopped it.
  - When the compiler cannot load, the setup report still prints, and the command exits 2.
  
  `@hozo/migration-audit` now exports `validateBaseline`.

## 0.3.0

### Minor Changes

- [#923](https://github.com/iray-tno/hozo/pull/923) [`8d58223`](https://github.com/iray-tno/hozo/commit/8d5822322607b6214fa7f57d233a9173a45815b6) Thanks [@iray-tno](https://github.com/iray-tno)! - Add the compiler-owned `@hozo/compiler/analysis` entry and project-aware migration analysis. The audit records canonical lowering diagnostics, authored locations or explicit unmapped locations, source/binding provenance, React Native import/tag/reference/value rewrite journals, project facts and stage timings rather than reconstructing compiler decisions from output alone.
  
  The CLI discovers nonempty `src/` and `app/` layouts, falls back to the checkout root, accepts repeated source/include/exclude selections and inventories JS/TS separately from imported context modules. Interactive stdout is Markdown; piped stdout remains JSON, with explicit format/output overrides. Bluesky-specific ALF checks remain in the corpus measurement path, not the generic report.
  
  Static theme, preflight assumptions, platform-scoped StyleX imports, installed/local tsconfig presets and supplied font-registration facts can inform analysis. Executable CSS configuration and remote stylesheets are reported as not assessed, never executed; missing and invalid context is not treated as successful absence. Baseline comparison distinguishes compatible comparisons from unassessed context and can fail CI on current errors or new error findings.
  
  **Report consumers must migrate to JSON schema 3.** Older baselines cannot supply a schema-3 semantic comparison. A clean compiler audit still does not prove production dependency removal, runtime behavior, Native Metro preparation or device font availability. See the migration-audit README for the supported facts and comparison boundaries.
