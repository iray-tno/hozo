# AGENTS.md

Instructions for coding agents (Codex, Claude Code, Antigravity, and anything
else) working in this repository. Humans are welcome to read it too; the rules
are the same for everyone.

[`CONTRIBUTING.md`](CONTRIBUTING.md) is the source of truth for the shape of the
repository, how to verify a change, and the traps a newcomer falls into. Read it
before your first change. This file does not repeat it; it adds what an agent
most often gets wrong, and the naming conventions every agent must share.

## Toolchain (local development)

Local tool versions are declared in [`.mise.toml`](.mise.toml) (`node = "25"`, `rust = "stable"`), matching CI.
`pnpm` (`11.21.0`) is pinned by `packageManager` in `package.json` and runs through mise's shims.
If tools (`node`, `pnpm`, `cargo`) are missing from your `PATH` in a subshell, ensure mise shims are loaded or run through `mise exec -- <command>`.

## Before you open a pull request

Run, from the repository root, in this order:

```sh
cargo test --workspace                       # if anything under crates/ changed
pnpm --filter @hozo/compiler build:native    # after any change under crates/
pnpm lint
pnpm test                                    # not `pnpm turbo run test`
pnpm docs:check
```

Things that look harmless and are not (details in `CONTRIBUTING.md`):

- **Never edit `packages/*/package.json` by hand.** It is generated by
  `scripts/package-metadata.mjs`. Change the generator.
- **Rebuild the native addon after a Rust change.** Otherwise every JS test is
  measuring the previous build, including the ones that pass.
- **Generated docs are checked.** If `pnpm docs:check` fails, run the generator
  it names (`pnpm docs:primitives`, `pnpm docs:layout`, `pnpm docs:readmes`);
  do not hand-edit the generated section.
- **A conformance number that moves, in either direction, needs the snapshot
  committed and a reason in the PR.**
- **A change users will notice needs a changeset** (`pnpm changeset`). Under
  `0.x`, breaking is `minor`. See [`.changeset/README.md`](.changeset/README.md).

## Pull requests

### Title — checked by CI

```
type(scope): summary
```

The title becomes the subject line on `main`, so it is the one name that has to
be right. `.github/workflows/pr-title.yml` runs
[`scripts/check-pr-title.mjs`](scripts/check-pr-title.mjs) and fails the PR
otherwise. Check locally with `node scripts/check-pr-title.mjs "<title>"`.

- **type**: `feat` `fix` `perf` `refactor` `test` `docs` `ci` `build` `chore` `revert`
- **scope** (optional, comma-separated): a directory name under `packages/`,
  `apps/`, `examples/`, or `crates/` (crates without `hozo_`: `parser`, not
  `hozo_parser`), or one of `repo` `ci` `deps` `docs` `release` `decisions`
  `rfcs`. The list is read from the tree, so a new package is a valid scope as
  soon as its directory exists.
- **summary**: what is different afterwards, not which file you touched. No
  trailing period. Whole title ≤ 100 characters. Append `!` after the scope for
  a breaking change.

| Good | Not |
| --- | --- |
| `fix(compiler): keep the component when a spread hides what the shape depends on` | `fix: bug` |
| `feat(ui): add Input, Checkbox, Switch, Badge and Alert` | `Update files` |
| `docs(decisions): 005, a control's value goes in the value channel` | `docs: update docs.` |
| `fix(landing): make CodeShowcase responsive on narrow viewports` | `fix(CodeShowcase.tsx): css` |

### Body

Use [`.github/pull_request_template.md`](.github/pull_request_template.md) and
fill in all three sections. **"What was measured" is the one that matters**:
the commands you ran and what they printed, and any number that moved with the
reason it moved. A claim that something works is worth as much as the command
that showed it. Write it in English.

### Branch

`type/short-kebab-slug`, using the same types: `fix/lp-code-showcase-responsive`,
`feat/theme-dark`. Not checked; just be consistent.

### Commits

Prefer the same `type(scope): summary` form as the title. Only the PR title is
enforced, because that is what lands on `main`. Keep unrelated changes in
separate commits — a formatting sweep inside a behavioural change makes the
behavioural change unreviewable.

## Issues

- **Bug** — the title states the observed behaviour as one sentence, cause
  first when known:
  `A package in node_modules contributes no candidates, so a source-distributed library emits no CSS`.
  Not `CSS bug`.
- **Proposal** — `rfc: <subject> — <one-line summary>`:
  `rfc: @hozo/ui — a styled component library, shipped as source`.
- **Area work** — an area prefix is fine where it helps: `Three: evaluate and prove a Native GPU host`.
- The body says how to reproduce or what was measured, and what would count as done.

## Labels

Apply **one kind** label and **any number of nature** labels. Do not create new
labels; ask in the PR or issue if one seems missing.

| Kind (one) | When |
| --- | --- |
| `bug` | Something behaves differently from what it claims |
| `enhancement` | New capability, or an RFC |
| `documentation` | Only docs change |

| Nature (any) | When |
| --- | --- |
| `measurement` | Something has to be measured before it can be decided |
| `needs-device` | Cannot be settled without real hardware or a real screen reader |
| `performance` | Speed or size of the compiler or runtime — with a number |
| `direction` | Where the project is going; no owner yet |

## Writing

- Code comments and docs explain *why*, not *what*. Keep existing comments
  that your change does not make wrong.
- Follow Biome (`pnpm lint:fix`): 2-space indent, single quotes, semicolons
  only where needed.
- When a measurement and the thing measured disagree, suspect the measurement
  first. A count of zero deserves the same suspicion.
