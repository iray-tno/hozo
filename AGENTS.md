# AGENTS.md

Instructions for coding agents (Codex, Claude Code, Antigravity, and anything
else) working in this repository. Humans are welcome to read it too; the rules
are the same for everyone.

[`CONTRIBUTING.md`](CONTRIBUTING.md) is the source of truth for the shape of the
repository, how to verify a change, and the traps a newcomer falls into. Read it
before your first change. This file does not repeat it; it adds what an agent
most often gets wrong, and the naming conventions every agent must share.

## Toolchain (local development)

Local tool versions are declared in [`.mise.toml`](.mise.toml) (`node = "25"`, `rust = "stable"`), matching CI.
`pnpm` (`11.21.0`) is pinned by `packageManager` in `package.json` and runs through mise's shims.
If tools (`node`, `pnpm`, `cargo`) are missing from your `PATH` in a subshell, ensure mise shims are loaded or run through `mise exec -- <command>`.

## Before you open a pull request

Run, from the repository root, in this order:

```sh
cargo fmt --all --check                      # if anything under crates/ changed; `cargo fmt --all` fixes it
cargo test --workspace                       # if anything under crates/ changed
pnpm --filter @hozo/compiler build:native    # after any change under crates/
pnpm lint
pnpm test                                    # not `pnpm turbo run test`
pnpm docs:check
```

Things that look harmless and are not (details in `CONTRIBUTING.md`):

- **Never edit `packages/*/package.json` by hand.** It is generated by
  `scripts/package-metadata.mjs`. Change the generator.
- **Rebuild the native addon after a Rust change.** Otherwise every JS test is
  measuring the previous build, including the ones that pass.
- **Generated docs are checked.** If `pnpm docs:check` fails, run the generator
  it names (`pnpm docs:primitives`, `pnpm docs:layout`, `pnpm docs:readmes`);
  do not hand-edit the generated section.
- **A conformance number that moves, in either direction, needs the snapshot
  committed and a reason in the PR.**
- **`<div>` and `<span>` do not exist on React Native.** In any module Native
  can load, write `View`/`Text` or another `@hozo/core` primitive; only the
  Web half of a split component (`x.tsx` beside `x.native.tsx`) writes the
  DOM. `scripts/native-hosts.test.mjs` enforces it; see
  [decision 010](docs/decisions/010-primitives-not-tags.md).
- **A change users will notice needs a changeset** (`pnpm changeset`). Under
  `0.x`, breaking is `minor`. See [`.changeset/README.md`](.changeset/README.md).

## Pull requests

### Title — checked by CI

```
type(scope): summary
```

The title becomes the subject line on `main`, so it is the one name that has to
be right. `.github/workflows/pr-title.yml` runs
[`scripts/check-pr-title.mjs`](scripts/check-pr-title.mjs) and fails the PR
otherwise. Check locally with `node scripts/check-pr-title.mjs "<title>"`.

- **type**: `feat` `fix` `perf` `refactor` `test` `docs` `ci` `build` `chore` `revert`
- **scope** (optional, comma-separated): a directory name under `packages/`,
  `apps/`, `examples/`, or `crates/` (crates without `hozo_`: `parser`, not
  `hozo_parser`), or one of `repo` `ci` `deps` `docs` `release` `decisions`
  `rfcs`. The list is read from the tree, so a new package is a valid scope as
  soon as its directory exists.
- **summary**: what is different afterwards, not which file you touched. No
  trailing period. Whole title ≤ 100 characters. Append `!` after the scope for
  a breaking change.

| Good | Not |
| --- | --- |
| `fix(compiler): keep the component when a spread hides what the shape depends on` | `fix: bug` |
| `feat(ui): add Input, Checkbox, Switch, Badge and Alert` | `Update files` |
| `docs(decisions): 005, a control's value goes in the value channel` | `docs: update docs.` |
| `fix(landing): make CodeShowcase responsive on narrow viewports` | `fix(CodeShowcase.tsx): css` |

### Body

Use [`.github/pull_request_template.md`](.github/pull_request_template.md) and
fill in all three sections. **"What was measured" is the one that matters**:
the commands you ran and what they printed, and any number that moved with the
reason it moved. A claim that something works is worth as much as the command
that showed it. Write it in English.

### Branch

`type/short-kebab-slug`, using the same types: `fix/lp-code-showcase-responsive`,
`feat/theme-dark`. Not checked; just be consistent.

### Stacked pull requests

Use the GitHub CLI extension **`github/gh-stack`** (`gh stack`) for dependent
PRs, rather than maintaining a chain of base branches by hand. An independent
single PR does not need an artificial stack.

- Before changing a stack, inspect `git status`, `gh stack view --json` and
  the affected PRs' heads, bases and CI results. Work only on your own stack;
  do not adopt another agent's branches or PRs without a handoff.
- Start with `gh stack init --base main <branch>`. Existing branches can be
  adopted by listing them **bottom to top**, but inspect their history first.
  Add the next layer with `gh stack add <branch>` after committing the current
  layer's scoped changes. Do not use its stage-all flags on a shared/dirty tree.
- Use `gh stack rebase` for cascading rebases and `gh stack submit` to push
  and create/update the PRs. Inspect the result with `gh stack view --json`.
  `gh stack sync` also rebases **and pushes**; it is not a read-only status
  command. Do not use `--prune` merely to sync: it deletes merged local branches.
- For non-interactive submission, `gh stack submit --auto --open` makes
  review-ready PRs, not drafts. Use it only when every affected PR should be
  ready; do not override an intentional draft. Waiting for CI alone does not
  require a draft. Check the installed `--help` rather than guessing flags.
- Auto-generated titles/bodies do not replace this repository's PR contract:
  set each title and English three-section body with `gh pr edit`, and apply
  your own `taken` label to **every layer** (see Agent ownership below).
  After submission/sync, verify each PR's diff, base, labels and current-head
  checks. Recheck completed parent CI before starting the next layer; fix a
  known failure instead of propagating it. State dependencies and merge order
  in the PR bodies even when GitHub shows the stack.
- Creating/submitting a stack is not permission to merge it. Do not run
  `gh stack merge`, merge individual PRs, or enable auto-merge without the
  user's explicit authorization.

### Commits

Prefer the same `type(scope): summary` form as the title. Only the PR title is
enforced, because that is what lands on `main`. Keep unrelated changes in
separate commits — a formatting sweep inside a behavioural change makes the
behavioural change unreviewable.

## Issues

- **Bug** — the title states the observed behaviour as one sentence, cause
  first when known:
  `A package in node_modules contributes no candidates, so a source-distributed library emits no CSS`.
  Not `CSS bug`.
- **Proposal** — `rfc: <subject> — <one-line summary>`:
  `rfc: @hozo/ui — a styled component library, shipped as source`.
- **Area work** — an area prefix is fine where it helps: `Three: evaluate and prove a Native GPU host`.
- The body says how to reproduce or what was measured, and what would count as done.

## Agent ownership

Several agents work in this repository at once, all through one GitHub
account, so an assignee cannot say which of them owns the work. A `taken`
label does, on both issues and PRs.

- **Your name** is `<agent>-<n>` -- for example `codex-1`, `claude-1`,
  `claude-2`, or `agy-1` -- and
  it is given by whoever started you. Do not pick a number yourself: two
  agents choosing at the same moment would choose the same one. If you were
  given no name, ask before claiming work.
- **Reuse your existing label's exact name.** Historical spellings include
  `taken:codex-1`, `taken: claude-1` and `taken: agy-1`; the space after the
  colon is not a different identity. Check for both spellings before creating
  one. Do not create duplicates or rename other agents' labels. If neither
  exists, create `taken: <your name>` with colour `#5319e7` and description
  `Being worked on by <your name>` -- the one exception to the label-creation
  rule below.

### Taking an issue

- **Before starting**, look for a `taken: …` label on the issue. If another
  agent has it, leave it, or ask the person who started you.
- **When starting**, add your own label and comment one line: who took it,
  the branch, and the session if you have a link.
- **When stopping without a fix**, remove the label and say why in a comment,
  so the issue is free again. A PR that says `Fixes #n` closes the issue and
  ends the claim with it; nothing else to undo.

### Owning a pull request

- Put your own `taken` label on **every PR you create**, including standalone
  fixes/docs with no issue and every PR in a stack. An issue's label is not
  automatically inherited by its PRs, and `gh stack submit` does not replace
  this step. Use `gh pr edit <number> --add-label "<your exact label>"` and
  verify the resulting labels after creation.
- Keep the PR's label as authorship/ownership history after merge or closure.
  An issue's label is an active work claim; a closed PR's label is not one.
  Change another agent's ownership only after an explicit handoff, not merely
  because you reviewed or rebased their work.

## Labels

Apply **one kind** label and **any number of nature** labels. Do not create new
labels, except your own `taken` label (see "Agent ownership"); ask in the
PR or issue if one seems missing.

| Kind (one) | When |
| --- | --- |
| `bug` | Something behaves differently from what it claims |
| `enhancement` | New capability, or an RFC |
| `documentation` | Only docs change |

| Nature (any) | When |
| --- | --- |
| `measurement` | Something has to be measured before it can be decided |
| `needs-device` | Cannot be settled without real hardware or a real screen reader |
| `performance` | Speed or size of the compiler or runtime — with a number |
| `direction` | Where the project is going; no owner yet |
| `blocked-upstream` | Waiting on a fix or feature outside this repository (React Native, WebKit, a dependency); the issue says what to do when it lands |
| `flaky` | A test that fails or passes without a code change; one issue per test, listed in [`docs/flaky-tests.md`](docs/flaky-tests.md) |

## Writing

- Code comments and docs explain *why*, not *what*. Keep existing comments
  that your change does not make wrong.
- Follow Biome (`pnpm lint:fix`): 2-space indent, single quotes, semicolons
  only where needed.
- When a measurement and the thing measured disagree, suspect the measurement
  first. A count of zero deserves the same suspicion.
